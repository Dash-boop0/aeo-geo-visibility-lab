# Methodology: measuring brand visibility in AI-generated answers

This document describes how to run a repeatable AEO/GEO (answer-engine / generative-engine optimisation)
visibility study with the lab, exactly how each metric is calculated, and what the numbers can and cannot tell you.

> The sample project shipped with the app is **illustrative and synthetic**. Its brands are fictional and its
> observations were generated by a seeded random process. The worked examples below use a small hand-built
> fixture, not real AI results.

## 1. What is being measured

The unit of analysis is an **observation**: one answer from one AI assistant to one fixed prompt, on one date,
in one run. For each observation you log:

| Field | Why it matters |
|---|---|
| Question (with intent) | Ties the answer to a fixed buyer question so rounds are comparable. |
| Exact prompt | Small wording changes can change answers; the prompt is the experimental stimulus. |
| Platform label | Which assistant or surface answered (labels are yours, e.g. "Assistant A"). |
| Date | Answers drift over time; the date defines the measurement round. |
| Run number | Separates repeated asks of the same prompt on the same day. |
| Settings | Model/mode, signed-in or not, locale, new chat or continued, any personalisation. |
| Answer summary | A short neutral description so a reviewer can audit the coding. |
| Brands mentioned | Which tracked brands the answer names (coded by a person). |
| Cited URLs / domains | Sources the answer links or names. URLs are reduced to domains for analysis. |

## 2. Experiment design

1. **Define the decision you care about.** E.g. "Are we recommended when small agencies look for invoicing tools?"
2. **Fix the brand set.** One or more *target* brands (yours) and the *competitors* you want to benchmark.
   Register every website domain each brand owns; subdomains are matched automatically.
3. **Write a fixed question set** across the four buyer intents:
   - *Discovery* — finding options ("best invoicing tools for freelancers").
   - *Informational* — learning ("what should an invoice include?").
   - *Comparison* — brand vs brand or alternatives ("X vs Y", "alternatives to X").
   - *Purchase* — pricing, plans, buying decisions ("is X worth paying for?").
   Aim for at least 8–10 questions per intent you want to report on, so per-intent rates are not all "low n".
4. **Choose platforms and a schedule.** Same platforms each round, at a regular interval (e.g. monthly).
5. **Write coding rules before you start** and keep them with the project (see §4).
6. **Log every answer**, including answers that mention no tracked brand and cite nothing — those are data too.
   Dropping "empty" answers inflates every rate.

## 3. Repeatability checklist

AI answers are not deterministic. Treat each observation as a sample and control what you can:

- **Fixed prompts.** Ask the exact same text every round. If you must change a prompt, create a new question
  instead of editing the old one, so history is not silently mixed.
- **Log date, platform and settings** for every observation: model or mode, signed in/out, location/locale,
  new conversation, any memory or personalisation features.
- **Fresh context.** Start a new chat per question; earlier turns change later answers.
- **Repeated runs.** Ask each prompt more than once (run 1, 2, 3…) on the same day for at least a subset of
  questions. The *run-to-run agreement* metric shows how stable target mentions are; low agreement means
  single-run differences between dates or platforms are mostly noise.
- **Same coder, same rules.** Ideally one person codes mentions and citations with written rules; if several
  people code, double-code a sample and compare.
- **Keep the raw evidence.** Store screenshots or copies of answers outside the app (the app stores summaries).
- **Back up** the project JSON after each round and keep exports with a date in the filename.

## 4. Coding rules (suggested defaults)

- A brand is **mentioned** when the answer names it (or a registered alias) as an option, example or subject —
  including negative mentions. Record sentiment in notes if you need it; it is not scored.
- Count a brand **once per observation**, however many times it appears.
- A **citation** is a source the answer links (URL) or explicitly names as a source (domain only).
  Footnotes, "sources" panels and inline links all count. Do not add sources you found yourself.
- Use "Suggest from summary" only as a helper; it matches names in your summary text and you confirm the result.

## 5. Metric definitions

Notation: *S* = observations in scope (after filters), *n* = |S|.

| Metric | Numerator | Denominator |
|---|---|---|
| Brand mention rate (per brand) | observations in S whose mentions include the brand | n |
| Target brand mention rate | observations in S mentioning ≥1 target brand | n |
| Target-domain citation rate | observations in S citing ≥1 URL or domain on a target-brand domain (exact or subdomain) | n |
| Brand domain citation rate (per brand) | observations in S citing ≥1 of that brand's domains | n |
| Any-citation rate | observations in S citing ≥1 source | n |
| Mention share / competitor mention share (per brand) | mentions of the brand in S | all tracked-brand mentions in S |
| Citation-source frequency (per domain) | observations in S citing that domain (once per observation) | n |
| Cited URLs (per domain) | count of cited URLs on that domain | — (a count, shown alongside) |
| Run-to-run agreement | (question, platform, date) groups with ≥2 runs where all runs agree on target mention | such groups |

Rules applied everywhere:

- **Zero denominator → "n/a"**, never 0%.
- **Low n**: any rate whose denominator is below **10** is flagged "⚠ low n" and should be read as directional.
- Every rate is displayed with its numerator/denominator.
- **Domains**: lower-cased, `www.` removed, ports/paths dropped. A domain belongs to a brand if it equals one of
  the brand's domains or is a subdomain of it (`docs.brand.example.com` → `brand.example.com`;
  `notbrand.example.com` does not match). When two brand domains match, the most specific wins.
- Mentions of brands no longer tracked are ignored; deleting a brand removes it from all observations.

### Worked example (from `tests/fixtures.js`)

Six observations, brands T (target), C1, C2:

| Obs | Question | Platform | Date | Mentions | Cited |
|---|---|---|---|---|---|
| o1 | q1 | A | 2026-01-01 | T, C1 | www.t.example.com/x, review.example.org/a |
| o2 | q2 | A | 2026-01-01 | C1 | c1.example.com/p, review.example.org (domain) |
| o3 | q3 | A | 2026-01-01 | — | — |
| o4 | q1 | B | 2026-01-01 | T | docs.t.example.com (domain) |
| o5 | q1 | A | 2026-02-01 | T, C1, C2 | review.example.org/b, review.example.org/c |
| o6 | q2 | A | 2026-02-01 | C2 | — |

- Target brand mention rate = 3/6 = 50.0% (o1, o4, o5) — flagged low n.
- Target-domain citation rate = 2/6 = 33.3% (o1 via `www.`, o4 via subdomain).
- Mention share: 8 tracked mentions in total → T 3/8, C1 3/8, C2 2/8.
- Citation-source frequency: `review.example.org` cited in 3/6 observations (3 URLs; o2 named it without a link).
- Coverage: platform B has no observations on 2026-02-01 → listed as missing, not imputed.

These values are asserted in `tests/metrics.test.js` and `tests/exporters.test.js`.

## 6. Comparing dates and platforms

- A comparison is made only when **both sides have data**. Otherwise the app shows "not comparable" and why
  (e.g. "No observations for 2026-02-01").
- By default comparisons use **matched questions**: only questions observed on both sides are included, so a
  change is not caused by a different question mix. Excluded observations are counted on screen. You can turn
  matching off to compare all observations.
- With matching on, repeated runs on one side remain in that side's sample (each run is an observation).
- Changes are reported in **percentage points** (B − A). No significance test is performed; with typical sample
  sizes (tens of observations per cell) differences of a few points are within run-to-run noise.
- The **coverage grid** (platform × date) shows every combination and marks missing ones explicitly.

In the worked example, comparing 2026-01-01 → 2026-02-01 on platform A uses q1 and q2 only (o3 excluded):
target mention 1/2 → 1/2 (0.0 pp), target-domain citation 1/2 → 0/2 (−50.0 pp), target mention share
1/3 → 1/4 (−8.3 pp), all flagged low n.

## 7. Limitations

- **Answers vary run to run** and with account state, location, model version, time and phrasing. A rate
  describes your sample of answers, not "the platform".
- **Manual logging bias.** What counts as a mention, how a summary is worded and which citations are noticed
  all depend on the coder. Written coding rules and double-coding reduce but do not remove this.
- **Small samples.** A 30-question set gives wide uncertainty, especially per intent or per platform × date cell.
  The low-n flag is a minimum warning, not a guarantee that larger samples are precise.
- **Fixed question set.** Results describe only the questions you chose; they are not search rankings, traffic,
  or market share, and they do not say *why* an assistant mentions a brand.
- **Citations ≠ influence.** A cited domain may not be what the answer drew on, and uncited sources may have been.
- **No automation.** The lab does not query AI platforms, scrape pages or verify that cited URLs exist.
- **Platform labels are free text.** "Assistant A" in one round must mean the same product and mode in the next.
